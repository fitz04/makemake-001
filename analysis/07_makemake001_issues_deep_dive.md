## 2. 모든 보고된 이슈 목록

### 2.1 엔진(VoxelTools) 한계로 인한 문제

#### VT-01: `set_node_param()` API 변경 (심각도: 높음, 해결됨)
- **증상:** `graph.set_node_param(id, 0, radius)`로 SdfSphere 반경 설정 불가
- **원인:** Voxel Tools 1.5+에서 SdfSphere의 radius가 parameter에서 input으로 변경
- **해결:** `graph.set_node_default_input(id, 3, radius)` 사용
- **영향:** 코드와 .tres 파일 사이 행성 반경 수동 동기화 필요 (해결 전)

#### VT-02: Smoothstep 파라미터 순서 반전 (심각도: 높음, 해결됨)
- **증상:** 크레이터 겹침 시 넓은 지역이 함께 가라앉고 청크 경계 깨짐
- **원인:** `NODE_SMOOTHSTEP`의 param 0 = edge1, param 1 = edge0 (표준과 반대)
- **해결:** 항상 param 0 > param 1 순서로 설정
- **영향:** 문서화되지 않은 동작으로 수시간 디버깅 소요

#### VT-03: `is_area_meshed()` 50% 행(hang) (심각도: 중간, 미해결)
- **증상:** 특정 청크 영역의 메시 완료를 기다리려 하면 50% 진행에서 멈춤
- **원인:** 청크 범위 제한 이슈로 추정
- **해결:** 기능 자체를 포기, 프레임 기반 대기로 대체
- **영향:** 신뢰할 수 있는 지형 준비 감지 불가

#### VT-04: 비동기 메시 생성 타이밍 (심각도: 높음, 임시 해결)
- **증상:** 복셀 메시 생성 전에 우주선이 지형을 뚫고 떨어짐
- **원인:** VoxelLodTerrain은 메시를 비동기적으로 생성하며, 충돌 메시 준비 전에 물리 연산 시작
- **해결:** 150m 스폰 높이 + 120프레임 대기 (하드웨어 의존적)
- **영향:** 느린 시스템에서 여전히 관통 가능

#### VT-05: SDF 부호 규칙 비직관적 (심각도: 낮음, 해결됨)
- **증상:** 크레이터가 볼록하게 튀어나옴 (의도는 오목)
- **원인:** SDF에서 Add 노드: 양수 = 함몰(depression), 음수 = 융기(uplift)
- **해결:** 깊이를 양수로 설정
- **영향:** SDF 부호 규칙 이해 부족으로 시간 소요

#### VT-06: Voxel Graph에 삼각함수 노드 부재 (심각도: 중간, 미해결)
- **증상:** 정확한 구면 좌표 변환 불가
- **원인:** `atan2`, `asin` 노드가 Voxel Graph에 없음
- **해결:** 원통형 투영(Cylindrical Projection) 사용으로 대체 (극지방 왜곡 수용)
- **영향:** 하이트맵의 극지방 왜곡, 정밀한 구면 매핑 불가

#### VT-07: SQLite 지형 캐시 문제 (심각도: 높음, 해결됨)
- **증상:** 코드 수정 후에도 이전 지형이 계속 로드됨
- **원인:** `debug_data/Makemake.sqlite`에 오래된 지형 데이터가 캐싱
- **해결:** `rm -f debug_data/Makemake.sqlite` (매 변경마다)
- **영향:** 변경 사항이 반영되지 않아 버그의 원인인지 캐시의 원인인지 구분 불가 -- 디버깅 시간 극대화

#### VT-08: 하이트맵 스탬핑에서 구형 좌표계 처리 (심각도: 높음, 부분 해결)
- **증상:** 하이트맵 스탬프가 구형 행성 표면에 올바르게 적용되지 않음
- **원인:** 평면 하이트맵을 구형 표면에 적용할 때 법선 벡터 계산 복잡성
- **해결:** 21개 커밋에 걸친 반복적 시도 (행성 중심 기반 법선, 중력 기반 오프셋, Y축 투영 등)
- **영향:** 프로젝트 중단의 직접적 원인으로 추정

### 2.2 Godot 엔진 자체 문제

#### GD-01: FogVolume API 불일치 (심각도: 낮음, 해결됨)
- **증상 1:** `FogVolume.SHAPE_BOX` 상수 없음
- **증상 2:** `fog_volume.density = 0.15` 직접 설정 시 에러
- **원인:** Godot 4에서 FogVolume은 항상 Box이며, 속성은 FogMaterial을 통해서만 설정
- **해결:** FogMaterial 별도 생성 후 material에 할당

#### GD-02: RefCounted에 add_child 불가 (심각도: 낮음, 해결됨)
- **증상:** `body.add_child(fog_volume)` 호출 시 에러
- **원인:** StellarBody가 RefCounted 기반 데이터 클래스
- **해결:** root: Node3D 파라미터 추가

#### GD-03: Static 함수에서 Non-static 함수 호출 불가 (심각도: 낮음, 해결됨)
- **증상:** "_add_crater_dust_volumes()" 호출 시 컴파일 에러
- **원인:** `_setup_rocky_planet()`이 static인데 non-static 함수 호출
- **해결:** 함수를 static으로 변경

### 2.3 구현 방식의 오류

#### IM-01: 초기화 순서 문제 -- Null 참조 (심각도: 중간, 해결됨)
- **증상 1:** camera.gd:106 -- `_target`이 null일 때 `global_transform` 접근
- **증상 2:** solar_system.gd:377 -- `static_bodies` 배열에 null 요소
- **원인:** 우주선 할당 전에 `_physics_process` 실행, 또는 배열에 null 요소
- **해결:** null 체크 가드절 추가

#### IM-02: 하이트맵 법선 벡터 계산 반복 실패 (심각도: 높음, 부분 해결)
- **증상:** 하이트맵이 구형 표면에 잘못된 방향으로 적용
- **시도한 방법들 (5가지):**
  1. Y축 기반 법선 -- 평면에서는 작동하지만 구형에서 실패
  2. 행성 중심 기반 법선 -- 방향은 맞지만 크기/오프셋 문제
  3. 중력 기반 법선 오프셋 -- 과도한 오프셋 발생
  4. 원통형 투영 Y축 -- 부분적 개선
  5. 과도한 법선 오프셋 제거 후 단순화 -- 최종 시도
- **영향:** 하루에 21개 커밋의 직접적 원인

#### IM-03: 하이트맵 스탬프 크기 제어 실패 (심각도: 중간, 부분 해결)
- **증상:** 지형 변경이 캐릭터를 매몰시키거나 너무 작아서 안 보임
- **시도한 방법들:**
  1. 구체 크기/임계값 축소
  2. 스탬프당 생성량 감소
  3. 지형 변경을 "훨씬 더 눈에 띄게" 설정
- **모순:** `a2844e8`(생성량 감소)과 `2389c09`(더 눈에 띄게) 커밋이 서로 반대 방향

#### IM-04: 하이트맵 미리보기 성능 문제 (심각도: 중간, 해결됨)
- **증상:** 미리보기 시스템으로 프레임 레이트 저하
- **시도한 방법들:**
  1. 캐싱 및 샘플링 감소 -- 최적화
  2. 공격적 최적화 (180배 성능 향상)
  3. 결국 미리보기 자체를 비활성화
- **영향:** 미리보기를 추가했다가 결국 끔 -- 순 시간 낭비

### 2.4 설계 결정의 문제

#### DS-01: 바이옴 크기 하드코딩 (심각도: 중간, 미해결)

- **인지 상태:** 문서에서 "알려진 제한사항"으로 기록

#### DS-03: 프레임 기반 대기는 근본적 결함 (심각도: 중간, 미해결)

- **영향:** 하드웨어 성능에 따라 동작이 달라짐
- **대안 (미구현):** 시그널 기반 지형 준비 감지, 또는 재스폰 시스템

#### DS-04: 행성 크기 양극단 테스트만 수행 (심각도: 낮음)
- **테스트 결과:** 2km(너무 작음), 80km(3GB RAM, 너무 큼), 8km(적절)

## 3. 바이옴 크기 조절 문제 상세 분석

### 3.1 어떤 방식으로 바이옴 크기를 제어하려 했는가

프로젝트에서 바이옴 크기 제어를 위해 **두 가지 접근법**이 시도/계획되었다:

#### 접근법 1: 거리 기반 절대 좌표 (실제 구현)

쉐이더에서 각 프래그먼트의 월드 좌표를 바이옴 중심과 비교:

```glsl
float dist_to_landing = length(local_pos.xz - u_landing_basin_center.xz);
if (dist_to_landing < u_landing_basin_radius) {
    // Landing Basin 바이옴
}
```

바이옴별 크기 파라미터:
- 착륙 분지: 500m -> 1,200m (2.4배 확대)
- 화염-얼음 분지: 800m -> 1,800m (2.25배 확대)
- 살아있는 광맥 협곡: 1,500m -> 2,500m 폭 (1.67배 확대)
- 광석 고지대: 고도 50m 이상 (절대 기준)
- 극저온 평원: 나머지 전부 (기본값)

#### 접근법 2: 노이즈 기반 Voronoi (문서에 계획만)

BIOME_IMPLEMENTATION.md에 기술:
```gdscript
# Cellular noise로 5개 구역 자동 생성
[sub_resource type="ZN_FastNoiseLite" id="biome_selector"]
noise_type = 3  # Cellular
period = 4000.0  # Large cells
```

이 방법은 **구현되지 않았다.**

### 3.2 왜 안 됐는가

#### 문제 1: 바이옴 크기가 행성 대비 너무 작음
- 행성 반경: 8,000m (둘레 약 50,000m)
- 착륙 분지: 1,200m (행성 둘레의 2.4%)
- **시각적으로 차이를 느끼기 어려움** -- HDR 값(>1.0)으로 극단적 색상을 사용한 이유

#### 문제 2: 절대 좌표 기반의 근본적 한계
- 바이옴이 행성 한쪽 면에만 존재 (XZ 평면 기준)
- 행성 반대편은 무조건 "극저온 평원" (기본값)
- 구형 행성에서 절대 XZ 좌표는 적도 부근에서만 의미 있음
- **행성을 돌아다니면 바이옴이 절반에만 있다는 사실이 드러남**

#### 문제 3: 바이옴 경계 블렌딩
- Smoothstep으로 100-400m 폭의 전환 구간 구현
- 하지만 바이옴 색상이 비슷해서 (Makemake의 실제 색상은 대부분 회갈색 계열) 경계를 구분하기 어려움
- 이를 보완하기 위해 극단적 HDR 색상 사용 -> 비현실적 외관

#### 문제 4: 지형 형성과의 연동 미구현
- Phase 2B(지형 형성)가 계획만 되고 구현되지 않음
- 색상만으로는 바이옴 구분 불충분
- 크레이터, 협곡, 평탄화 등 지형적 차이가 있어야 바이옴이 의미 있음
- **Fire-Ice Basin만 유일하게 지형 + 색상 모두 구현됨**

### 3.3 엔진 한계인가 구현 문제인가

**판정: 혼합 -- 엔진 한계 30%, 구현 문제 70%**

**엔진 한계 부분:**
- Voxel Graph에 삼각함수 노드 부재 -> 정확한 구면 좌표 불가
- Noise 기반 바이옴 선택을 구형 행성에 적용하는 것이 문서화되지 않음
- VoxelInstancer의 바이옴 인식 밀도 제어가 제한적

**구현 문제 부분:**
- 절대 좌표 대신 구면 좌표(경위도) 기반으로 바이옴을 배치했어야 함
- 노이즈 기반 Voronoi 접근법이 계획만 되고 시도되지 않음
- 바이옴 크기를 행성 반경 대비 비율로 설정하지 않음
- Phase 2B(지형 형성) 미구현으로 바이옴의 체감 부족

## 5. 엔진 한계 vs 사용법 문제 최종 분류

### 5.1 이것은 VoxelTools의 한계다 (엔진을 바꿔야 해결됨)

| ID | 이슈 | 근거 |
|----|------|------|
| **VT-03** | `is_area_meshed()` 50% 행(hang) | 플러그인 내부 구현 버그/제한. 사용자가 고칠 수 없음 |
| **VT-06** | Voxel Graph에 삼각함수(atan2, asin) 노드 부재 | 플러그인이 제공하지 않는 노드. 커스텀 Expression 노드가 있으면 우회 가능하나 현재 없음 |
| **VT-02** | Smoothstep 파라미터 순서 반전 | 플러그인 설계 결정/버그. 문서화 부족이 근본 원인이나, 동작 자체는 엔진 수준 |
| **VT-04** | 비동기 메시 생성 타이밍에 대한 적절한 콜백 부재 | `is_area_meshed()`가 작동하지 않고, 메시 완료 시그널이 없거나 문서화되지 않음 |

**총평:** VoxelTools는 프로토타이핑에는 강력하지만, (1) API 문서화 부족, (2) 구면 행성 전용 유틸리티 부재, (3) 메시 완료 콜백의 신뢰성 문제가 있다. 다만 이것이 "엔진을 바꿔야 한다"는 의미는 아니다 -- VoxelTools 자체가 오픈소스이므로 기여/수정이 가능하다.

### 5.2 이것은 사용법의 문제다 (올바른 접근법으로 해결 가능)

| ID | 이슈 | 올바른 접근법 |
|----|------|--------------|
| **VT-01** | `set_node_param()` 대신 `set_node_default_input()` | **이미 해결됨.** API 변경 로그를 확인했어야 함 |
| **VT-05** | SDF 부호 규칙 혼동 | SDF 기초 이론 학습으로 해결 가능. SDF에서 양수 = 표면 바깥(공기) 방향으로 밀어내는 것 = 지형이 안쪽으로 들어감(함몰) |
| **VT-07** | SQLite 캐시 문제 | 개발 워크플로우에 캐시 클리어를 포함시키면 됨. 또는 개발 중 캐시 비활성화 |
| **VT-08** | 하이트맵 구형 적용 | 구면 좌표계 기반 접근법으로 처음부터 설계했어야 함. VoxelTool.set_voxel_f()와 구면 좌표 변환을 결합 |
| **IM-01** | Null 참조 | 기본적인 null 체크 패턴 적용 |
| **IM-02** | 하이트맵 법선 계산 | 행성 중심에서 표면 점까지의 벡터를 법선으로 사용하는 것이 정답. 처음부터 이 방식을 택했어야 함 |
| **IM-03** | 스탬프 크기 제어 | 복셀 크기(해상도)와 스탬프 반경의 관계를 사전에 계산했어야 함 |
| **DS-01** | 바이옴 절대 좌표 하드코딩 | 구면 경위도 + 노이즈 기반 접근으로 전환 필요 |
| **DS-02** | 2D 투영 기반 크레이터 | 행성 표면 위치를 구면 좌표로 계산 후 적용 |
| **DS-03** | 프레임 기반 대기 | VoxelLodTerrain의 시그널 활용, 또는 물리 비활성화 후 지형 준비 확인 후 활성화 |

### 5.3 이것은 Godot 자체의 문제다 (VoxelTools와 무관)

| ID | 이슈 | 비고 |
|----|------|------|
| **GD-01** | FogVolume API (SHAPE_BOX 상수 없음, 속성 직접 설정 불가) | Godot 4 API 설계. 문서 참조로 빠르게 해결 가능했음 |
| **GD-02** | RefCounted에 add_child 없음 | GDScript 기본 -- RefCounted vs Node 차이 이해 필요 |
| **GD-03** | Static/Non-static 함수 호출 제약 | GDScript 언어 규칙. 일반적인 프로그래밍 에러 |
| **IM-04** | 미리보기 시스템 성능 | Godot의 복셀 렌더링 부하 + 쉐이더 복잡도. VoxelTools 특유 문제 아님 |

### 5.4 최종 통계

| 분류 | 이슈 수 | 해결된 수 | 미해결 |
|------|---------|-----------|--------|
| VoxelTools 한계 | 4 | 2 | 2 |
| 사용법 문제 | 10 | 7 | 3 |
| Godot 자체 문제 | 4 | 4 | 0 |
| **합계** | **18** | **13** | **5** |

## 6. 종합 결론

### 6.1 프로젝트 중단의 핵심 원인

프로젝트가 중단된 가장 직접적인 원인은 **2025-11-16 하이트맵 스탬핑 시스템의 21개 커밋 마라톤**이다. 이 날 개발자는:

1. 하이트맵을 구형 행성에 실시간으로 적용하려 했다
2. 법선 벡터 계산 방법을 5번 바꿨다
3. 미리보기 시스템을 추가하고, 최적화하고, 끄는 과정을 반복했다
4. 디버그 로깅을 넣었다 뺐다 했다
5. 결국 마지막 커밋이 "Add comprehensive debug logging for terrain application" -- 여전히 디버깅 중

이것은 **구형 복셀 행성에 평면 하이트맵을 동적으로 스탬핑하는 것**이 해당 시점의 기술 수준으로는 지나치게 어려운 과제였음을 의미한다. VoxelTools의 구면 좌표 지원 부재와 개발자의 SDF/구면 수학 경험 부족이 결합된 결과다.

### 6.2 재개 시 우선순위 권고

1. **SQLite 캐시 자동 클리어** -- 개발 생산성의 가장 큰 방해물
2. **프레임 대기 -> 시그널 기반** -- 스폰 신뢰성 확보
3. **바이옴을 구면 좌표 기반으로 재설계** -- 노이즈 + 경위도
4. **하이트맵 스탬핑 대신 크레이터 생성기 확장** -- 이미 작동하는 시스템 활용
5. **VoxelTools 최신 버전 확인** -- `is_area_meshed()` 수정 여부, 새 노드 추가 여부
