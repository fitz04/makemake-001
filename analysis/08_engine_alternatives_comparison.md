## 1. 대안 엔진별 상세 비교

### 1.1 Unreal Engine 5 + Voxel Plugin (Phyronnaz)

#### 개요

Voxel Plugin은 Victor Careil(Phyronnaz)이 개발한 UE5용 복셀 플러그인으로, **Nanite 및 Lumen과 직접 통합**되는 것이 최대 강점이다. 2023년에 Voxel Plugin 2.0으로 **실제 크기의 화성(반경 3,390km)**을 UE5에서 재현한 데모를 공개하여 기술력을 입증했다.

#### 평가 항목

| 항목 | 평가 | 상세 |
|------|------|------|
| **구형 행성 지원** | **최우수** | 6개 하이트맵을 사용하는 Planet Node로 실제 크기 행성 생성 검증 완료. 화성(반경 3,390km) 재현 사례 존재. Project Nomad의 800km은 충분히 커버. |
| **런타임 편집** | **우수** | 런타임 Nanite 메시 스컬프팅, 복셀 편집 지원. 채굴/건설 구현 가능. |
| **텍스처/비주얼 품질** | **최우수** | Nanite(무한 폴리곤), Lumen(실시간 GI), 볼류메트릭 구름/안개, 메가라이트. UE5의 렌더링 파이프라인은 현존 최고 수준. |
| **성능** | **양호** | Nanite가 LOD를 자동 관리하여 복셀 지형에도 효율적. 단, 에디터 자체가 무거워 빌드/이터레이션 속도가 느림. 고사양 PC 권장. |
| **솔로 개발자 접근성** | **낮음~중간** | Blueprint으로 프로토타이핑은 빠르지만, Voxel Plugin 자체가 아직 개발 중(버그 존재)이며 C++ 지식이 필요한 상황이 빈번. UE5의 학습 곡선은 Godot보다 현저히 가파름. 프로젝트 사이즈가 수십 GB에 달해 관리 부담. |
| **라이선스/비용** | **중간** | UE5: 무료(매출 $1M 이상 시 5% 로열티). Voxel Plugin: **$349 영구 라이선스** (1년 기능 업데이트 + 3년 버그 픽스). 예산 $100K 초과 프로젝트는 별도 계약 필요. |
| **커뮤니티/문서** | **양호** | UE5 자체 커뮤니티는 거대. Voxel Plugin 전용 문서(docs.voxelplugin.com) 존재하나 아직 불완전한 부분 있음. Epic 포럼에 활발한 스레드. |
| **실제 출시 게임 사례** | **제한적** | Voxel Plugin 2.0으로 출시된 상용 게임은 아직 확인되지 않음. 레거시 버전(1.x)으로 소규모 인디 게임 사례 존재. 화성 데모는 기술 데모 수준. |

#### 핵심 장점

1. **비주얼 품질 천장이 없다.** Project Nomad의 1순위 요구사항인 "분위기"를 달성하기에 현존 최강의 렌더링 파이프라인.
2. **행성 스케일 검증 완료.** 3,390km 반경 화성이 작동한다면 400km 반경 마케마케는 문제없음.
3. **Nanite + 복셀 통합.** LOD를 수동 관리할 필요 없이 Nanite가 자동 처리.
4. **PCG 프레임워크 통합.** UE5의 Procedural Content Generation 시스템과 연동하여 바이옴/식생 배치 가능.

#### 핵심 리스크

1. **엔진 전환 비용.** 현재까지 Godot으로 진행한 리서치와 코드를 전부 포기해야 함. 학습 곡선 3-6개월 추가.
2. **Voxel Plugin 2.0 안정성.** "아직 버그가 있을 수 있다"고 공식 문서가 명시. UE 5.6/5.7 전용.
3. **솔로 개발자 부담.** UE5 프로젝트는 빌드 시간, 디스크 사용량, 에디터 메모리 사용량이 모두 Godot의 10배 이상. 이터레이션 속도 저하.
4. **C++ 필수.** Blueprint만으로는 복셀 시스템 커스터마이징에 한계. 채굴 시스템, 바이옴 생성기 등 핵심 시스템에 C++ 필요.
5. **비용.** Voxel Plugin $349 + 성공 시 UE5 로열티 5%.

### 1.2 Unity + 커스텀 복셀 (Planet Nomads 방식)

#### 개요

Planet Nomads(Craneballs Studio, 2017)는 Unity에서 **120km 직경 구형 복셀 행성**을 구현한 실제 상용 게임이다. C++ 플러그인 "Sandy Engine"을 자체 개발하여 Unity의 한계를 극복했다.

#### Planet Nomads 기술 스택 상세

- **C++ 플러그인(Sandy Engine):** 순수 Unity 대비 50% 성능 향상
- **Modified Marching Cubes** + 옥트리 청크 관리
- **청크 크기:** 16m ~ 128km, 최소 복셀 해상도 1m
- **R-Tree + SQLite:** 수정 이력의 지리적 인덱싱
- **가시 거리:** 2km, 최대 속도 120km/h 유지
- **커스텀 메모리 할당:** Stack Allocator + 오브젝트 풀링
- **멀티스레딩:** Unity 메인 스레드 제약을 비동기 액션 풀로 우회

#### 평가 항목

| 항목 | 평가 | 상세 |
|------|------|------|
| **구형 행성 지원** | **가능 (자체 구현)** | Planet Nomads가 120km까지 증명. 800km은 미검증이나 아키텍처적으로 확장 가능. |
| **런타임 편집** | **우수** | Sandy Engine의 핵심 기능. 런타임 복셀 변형(채굴/건설) 완전 지원. |
| **텍스처/비주얼 품질** | **양호~우수** | Unity HDRP 사용 시 볼류메트릭 안개/구름, 레이 트레이싱 가능. URP 시 중상급. |
| **성능** | **양호** | C++ 플러그인 + Jobs/Burst 시스템으로 최적화 가능. 단, 자체 엔진 개발의 최적화 부담이 큼. |
| **솔로 개발자 접근성** | **매우 낮음** | Planet Nomads는 **전업 팀**이 수년간 개발한 결과물. 솔로 개발자가 Sandy Engine 수준의 복셀 엔진을 자체 개발하는 것은 **현실적으로 불가능에 가까움.** |
| **라이선스/비용** | **중간** | Unity Personal: 무료(연매출 $200K 미만). Pro: 연 $2,200/석. HDRP는 추가 비용 없음. |
| **커뮤니티/문서** | **양호** | Unity 생태계는 거대. 그러나 "구형 복셀 행성" 특화 자료는 극히 제한적. |
| **실제 출시 게임 사례** | **존재** | Planet Nomads (2019 Early Access 종료). 다만 평가는 Mixed(58%)로 기술적 문제와 콘텐츠 부족으로 개발 중단. |

#### 기존 복셀 에셋

Unity Asset Store에 Digger PRO, Voxeland, uTerrains, Voxelica 등이 있으나, **구형 행성을 지원하는 것은 없다.** 모두 평면 지형에 최적화되어 있으며, 구형 행성용으로 전환하려면 대규모 커스터마이징이 필요하다.

#### 핵심 리스크

1. **자체 복셀 엔진 개발 = 6-12개월.** Sandy Engine급 시스템을 솔로 개발자가 만드는 것은 프로젝트 범위를 벗어남.
2. **Planet Nomads의 경고.** 기술적으로 야심 찬 프로젝트였으나 콘텐츠가 부족한 채로 개발이 사실상 중단됨. 기술에 너무 많은 시간을 투자한 대표적 사례.
3. **에셋 호환.** Unity 에셋 스토어의 에셋은 바로 사용 가능하지만, 복셀 지형과의 통합은 별도 작업 필요.

### 1.3 Godot + Terrain3D (복셀 포기, 하이트맵 기반)

#### 개요

Terrain3D(TokisanGames)는 Godot 4용 고성능 하이트맵 기반 지형 시스템이다. 복셀을 완전히 포기하고 하이트맵으로 전환하면 어떻게 되는지 분석한다.

#### 평가 항목

| 항목 | 평가 | 상세 |
|------|------|------|
| **구형 행성 지원** | **불가 (직접)** | Terrain3D는 **평면 지형 전용.** 구형 행성을 만들려면 Cube Sphere(6면 하이트맵 스티칭) 기법을 직접 구현해야 하며, Terrain3D가 이를 지원하지 않음. |
| **런타임 편집** | **제한적** | 하이트맵 높이 조절은 가능하나, **동굴/터널/오버행은 불가능.** 하이트맵의 본질적 한계. |
| **텍스처/비주얼 품질** | **양호** | Godot 4 Forward+ 렌더러 수준. 스플랫맵 기반 텍스처링, 셰이더 커스텀 가능. |
| **성능** | **최우수** | 복셀 대비 메모리/CPU 사용량이 극도로 낮음. 하이트맵은 2D 데이터이므로 3D 복셀보다 수십~수백 배 효율적. |
| **솔로 개발자 접근성** | **높음** | 에디터 도구가 잘 갖춰져 있고, 복셀 시스템보다 단순. 그러나 구형 행성 변환은 직접 구현해야 해서 복잡도 증가. |
| **라이선스/비용** | **무료** | MIT 라이선스. |
| **커뮤니티/문서** | **양호** | GitHub에서 활발한 개발. Godot 커뮤니티에서 가장 인기 있는 지형 플러그인. |
| **실제 출시 게임 사례** | **다수** | 하이트맵 기반 지형은 게임 업계 표준. Terrain3D 자체의 상용 출시 사례는 아직 초기. |

#### 구형 행성을 하이트맵으로 만드는 방법

이론적으로 **Cube Sphere** 기법(6개 면을 하이트맵으로 구성한 큐브를 구형으로 팽창)으로 구현 가능하지만:

1. **Terrain3D가 이를 지원하지 않으므로** 커스텀 구현 필수
2. **6면 경계 스티칭** 문제 (이음새 아티팩트)
3. **극점 왜곡** 문제
4. **구면 물리/중력** 별도 구현 필요

결론적으로 Terrain3D를 "그대로" 사용해서 구형 행성을 만드는 것은 **불가능하며**, 하이트맵 구형 행성 시스템을 직접 개발해야 한다. 이 경우 Terrain3D의 이점이 대부분 사라진다.

#### 치명적 한계

- **동굴 불가.** 하이트맵은 Y축에 대해 단일 높이만 저장하므로 동굴, 터널, 오버행을 표현할 수 없음.
- **채굴 불가.** 지형을 "파는" 것이 물리적으로 불가능. 높이만 조절 가능하여 "깊이 있는 채굴"을 표현할 수 없음.
- **Project Nomad의 핵심 메카닉과 양립 불가.** 채굴 → 제련 → 제작 루프의 채굴 부분이 근본적으로 손상됨.

### 1.4 Godot + VoxelTools (현재 스택, 올바른 사용법)

#### 개요

현재 Project Nomad의 기술 스택이다. 이전 분석(02_tech_architecture_analysis.md)에서 심층 평가한 바 있으며, 여기서는 "올바른 사용법"에 초점을 맞춰 재평가한다.

#### 좌절감의 원인 분석

개발자가 VoxelTools에 좌절감을 느끼는 가능한 원인:

1. **크레이터 생성 난이도.** VoxelGenerator 내에서 SDF 함수 조합으로 크레이터를 만들어야 하는데, 구면 위의 3D 노이즈 + SDF 조합은 수학적 복잡도가 높다.
2. **바이옴 시스템 부재.** VoxelTools에 내장 바이옴 시스템이 없어 직접 구현해야 한다.
3. **문서 부족.** "이렇게 하면 된다"는 레시피가 아닌, "이런 기능이 있다"는 API 문서 중심.
4. **디버깅 어려움.** 복셀 데이터가 시각적으로 보이지 않아 문제 진단이 어렵다.
5. **Module 빌드 부담.** 코드 변경 시 Godot 전체를 재빌드해야 함.

#### "올바른 사용법" 가이드

| 문제 | 올바른 접근법 |
|------|-------------|
| **크레이터** | VoxelGeneratorGraph에서 SdfSphere를 반전(negate)하여 구형 함몰 생성. 노이즈로 가장자리 불규칙화. 복수 크레이터는 좌표 기반 시드로 분포. |
| **바이옴** | VoxelGenerator 내에서 구면 좌표(위도/경도) 기반 노이즈 맵으로 바이옴 인덱스 계산. 바이옴별 노이즈 파라미터와 머티리얼 인덱스를 분기. |
| **바이옴 크기 제어** | 바이옴 분포 노이즈의 주파수(frequency)를 낮추면 큰 바이옴, 높이면 작은 바이옴. Voronoi 노이즈로 셀 기반 분포 가능. |
| **동굴** | 3D Perlin Worm(이동하는 구체가 밀도를 깎는 방식) 또는 3D 노이즈 임계값 기반 공동 생성. |
| **텍스처링** | 복셀 채널에 머티리얼 인덱스 저장 → 셰이더에서 머티리얼별 텍스처 배열 매핑. 법선 기반 triplanar 매핑으로 이음새 제거. |
| **성능** | VoxelLodTerrain의 lod_count, view_distance 적절 설정. 멀리 있는 청크는 LOD가 자동으로 해상도를 낮춤. |

#### 평가 항목

| 항목 | 평가 | 상세 |
|------|------|------|
| **구형 행성 지원** | **우수** | SdfSphere 기반 생성, solar_system_demo에서 20km까지 검증. 800km은 Double Precision + Origin Shifting으로 대응. |
| **런타임 편집** | **우수** | do_sphere(), do_box() 등 VoxelTool API로 런타임 채굴/건설 완전 지원. do_sphere_async()로 대규모 편집 시 스터터 감소. |
| **텍스처/비주얼 품질** | **중간** | Godot 4 Forward+ 렌더러 수준. UE5 대비 확실히 열세. 그러나 커스텀 셰이더, 후처리 파이프라인으로 분위기 보정 가능. "독특한 아트 스타일"로 승부해야 함. |
| **성능** | **양호** | C++로 작성된 모듈이라 GDScript보다 빠름. Transvoxel LOD로 원거리 최적화. 그러나 메시 업로드가 메인 스레드에서 이루어져 청크 생성 시 마이크로 스터터 발생 가능. |
| **솔로 개발자 접근성** | **중간~높음** | Godot 자체는 가볍고 빠름. 그러나 VoxelTools의 학습 곡선이 존재하며, 크레이터/바이옴/동굴을 모두 직접 구현해야 함. Module 빌드가 번거로울 수 있음. |
| **라이선스/비용** | **최우수 (무료)** | Godot: MIT, VoxelTools: MIT. 로열티 없음. |
| **커뮤니티/문서** | **중간** | Zylann 1인 개발이지만 7년 이상 활발한 개발. GitHub Issues에서 직접 답변. 공식 문서 존재하나 튜토리얼 부족. |
| **실제 출시 게임 사례** | **매우 제한적** | VoxelTools로 출시된 상용 게임은 확인되지 않음. solar_system_demo는 기술 데모. |

#### 현재 스택을 유지해야 하는 이유

1. **이미 투자한 학습 시간.** 엔진 전환 시 최소 3-6개월의 추가 학습이 필요.
2. **MIT 라이선스.** 비용 없음.
3. **모든 핵심 기능 지원.** 구형 행성, 런타임 편집, LOD, 동굴 -- 기능 자체는 모두 존재.
4. **Godot의 이터레이션 속도.** 에디터 120MB, 2초 내 실행. UE5의 수십 GB, 수 분 로딩과 비교 불가.
5. **Double Precision 공식 지원.** 800km 행성의 핵심 요구사항 충족.

#### 현재 스택의 한계

1. **비주얼 천장.** Godot 4의 렌더링은 UE5에 미치지 못함. 아트 스타일로 보완해야 함.
2. **1인 개발자 의존.** Zylann이 프로젝트를 중단하면 직접 C++ 모듈을 유지보수해야 함.
3. **상용 게임 사례 부재.** "이 기술로 게임을 출시할 수 있다"는 증명이 아직 없음.
4. **Module 빌드 복잡성.** GDExtension은 아직 실험적이어서, Module로 Godot를 커스텀 빌드해야 하는 부담.

### 1.5 Custom Engine / Rust + Godot FFI

#### 개요

Rust로 복셀 엔진 코어를 작성하고, Godot의 GDExtension을 통해 통합하는 방식이다. "Chunkee"라는 오픈소스 프로젝트가 이 접근법의 실제 사례이다.

#### 기존 프로젝트: Chunkee

- **GitHub:** ZachJW34/chunkee
- **구조:** Cargo 워크스페이스 -- `chunkee-core`(월드 생성, 청크 관리, 메싱) + `chunkee-godot`(GDExtension 브릿지)
- **성숙도:** 초기 단계, 프로덕션 레디가 아님
- **Godot 연동:** godot-rust(gdext) 바인딩 사용

#### 평가 항목

| 항목 | 평가 | 상세 |
|------|------|------|
| **구형 행성 지원** | **직접 구현 필요** | 모든 것을 처음부터 코딩. 구형 SDF, LOD, 청크 관리, 메시 생성 모두 자체 개발. |
| **런타임 편집** | **직접 구현 필요** | 복셀 편집 API를 처음부터 설계. |
| **텍스처/비주얼 품질** | **Godot 수준** | 렌더링은 Godot에 위임하므로 Godot 4 Forward+ 수준. |
| **성능** | **잠재적 최우수** | Rust의 zero-cost abstraction, 메모리 안전성, SIMD 최적화. 이론적으로 C++과 동등 또는 그 이상. |
| **솔로 개발자 접근성** | **극히 낮음** | 복셀 엔진을 처음부터 작성하는 것은 **1-2년의 전업 엔진 프로그래밍.** 게임 개발이 아니라 엔진 개발을 하게 됨. |
| **라이선스/비용** | **무료** | Rust, Godot, godot-rust 모두 MIT/Apache. |
| **커뮤니티/문서** | **매우 제한적** | godot-rust 자체는 활발하나, "Rust 복셀 엔진 + Godot" 조합의 레퍼런스는 Chunkee 하나뿐. |
| **실제 출시 게임 사례** | **없음** | 이 조합으로 출시된 게임은 존재하지 않음. |

#### 핵심 리스크

1. **시간 함정.** "더 나은 도구를 만들자"는 유혹은 게임 개발의 가장 큰 함정. 엔진 개발은 끝이 없다.
2. **기술적 복잡도.** Transvoxel, LOD, 청크 스트리밍, 메모리 관리, 물리 통합 등 VoxelTools가 7년에 걸쳐 구현한 것을 재현해야 함.
3. **GDExtension 불안정성.** Godot의 GDExtension API가 버전 간 변경될 수 있어 유지보수 부담.
4. **"Not Invented Here" 증후군.** VoxelTools가 이미 제공하는 기능을 재구현하는 것은 시간 낭비.

#### 유일하게 정당화되는 시나리오

VoxelTools가 **근본적으로 해결할 수 없는 문제**(예: 800km 스케일에서 치명적 성능 저하)를 발견한 경우에만 고려. 현재는 그러한 증거가 없다.

### 1.6 참고 사례: Astroneer / Space Engineers / Dual Universe

이 세 게임은 "구형 복셀 행성 + 런타임 편집"을 **상용 게임으로 출시한 실제 사례**이다. Project Nomad의 기술적 방향을 검증하는 데 중요한 참고 자료이다.

#### Astroneer (System Era Softworks, 2019)

| 항목 | 상세 |
|------|------|
| **엔진** | Unreal Engine 4 (Unity에서 프로토타입 후 전환) |
| **복셀 방식** | Soft Voxel (밀도 기반, Marching Cubes 유사) |
| **행성 크기** | 소규모 (~수 km 직경) |
| **런타임 편집** | 핵심 메카닉. "Play-Doh 같은" 지형 변형. |
| **비주얼** | 텍스처리스 로우폴리 아트 스타일. 텍스처 없이 색상과 형태만으로 분위기 형성. |
| **팀 규모** | 소규모 인디 팀 (~15-25명) |
| **성과** | Steam 압도적으로 긍정적, 500만+ 판매 |

**Project Nomad에 대한 시사점:**
- **행성 크기를 줄여도 게임이 된다.** Astroneer의 행성은 수 km에 불과하지만 풍부한 탐험감을 제공.
- **아트 스타일이 기술을 보완한다.** 텍스처리스 디자인으로 복셀 특유의 "뭉툭함"을 강점으로 전환.
- **UE4에서 복셀 시스템을 자체 구현.** 기존 플러그인이 아닌 커스텀 시스템 사용.

#### Space Engineers (Keen Software House, 2019)

| 항목 | 상세 |
|------|------|
| **엔진** | VRAGE (자체 엔진, 현재 VRAGE3) |
| **복셀 방식** | 볼류메트릭 지형 (파괴 가능) |
| **행성 크기** | 최대 120km 직경 |
| **런타임 편집** | 드릴링, 폭발로 지형 파괴/변형 |
| **비주얼** | 중간 수준. 복셀 지형 + 블록 기반 건설. |
| **팀 규모** | 중규모 (~50명) |
| **성과** | Steam 매우 긍정적, 1000만+ 판매 |

**Project Nomad에 대한 시사점:**
- **120km 행성이 복셀로 작동한다.** 800km은 아니지만, 의미 있는 스케일.
- **자체 엔진이 필요했다.** 범용 엔진으로는 이 규모의 복셀 시스템을 구현하기 어려웠기에 VRAGE를 처음부터 개발.
- **Havok 물리 통합.** 범용 물리 엔진과 복셀의 통합이 핵심 과제.

#### Dual Universe (Novaquark, 2022)

| 항목 | 상세 |
|------|------|
| **엔진** | 자체 엔진 |
| **복셀 방식** | Dual Contouring 기반, 25cm 정밀도 |
| **행성 크기** | 실제 행성 규모 (수백~수천 km) |
| **런타임 편집** | 핵심 기능. 행성 표면을 자유롭게 편집. |
| **비주얼** | 양호. LOD 자동 관리로 원거리 행성도 렌더링. |
| **팀 규모** | 대규모 (~100명+) |
| **성과** | Mixed (기술적 야심 대비 게임플레이 부족 비판) |

**Project Nomad에 대한 시사점:**
- **행성 규모 복셀은 가능하지만 대규모 팀이 필요했다.** 100명 이상의 팀이 수년간 개발.
- **기술 > 게임플레이의 경고.** 기술적으로는 인상적이나, 실제 게임으로서의 재미가 부족하다는 평가. Planet Nomads와 같은 경고.
- **LOD 시스템이 핵심.** 행성 규모에서는 동적 LOD가 필수이며, 가까이 가야만 상세 디테일이 로드되는 방식.

#### 종합 교훈

| 교훈 | 설명 |
|------|------|
| **행성 크기 ≠ 재미** | Astroneer(수 km)가 Dual Universe(수천 km)보다 훨씬 높은 평가. 작은 행성이라도 밀도 높은 콘텐츠가 중요. |
| **아트 스타일로 기술 한계 극복** | Astroneer는 텍스처리스 디자인으로 복셀의 한계를 강점으로 전환. |
| **자체 엔진은 대규모 팀용** | Space Engineers, Dual Universe 모두 자체 엔진을 수십~수백 명이 개발. 솔로 개발자에게는 기존 엔진 + 플러그인이 현실적. |
| **기술에 빠지면 게임이 죽는다** | Planet Nomads, Dual Universe 모두 기술 개발에 집중하다 게임 콘텐츠가 부실. |

## 3. "복셀을 포기하면?" 시나리오 분석

### 3.1 채굴 시스템을 복셀 없이 구현할 수 있는가?

#### 가능한 대안들

| 방식 | 설명 | 적합도 |
|------|------|--------|
| **메시 변형(Mesh Deformation)** | 지형 메시의 정점을 런타임에 이동시켜 "파인" 효과 생성. | **낮음.** 표면 수준의 변형만 가능. 깊이 있는 채굴, 터널 관통 불가. |
| **프리팹 교체(Prefab Swap)** | 채굴 시 온전한 암석 프리팹을 "파괴된" 프리팹으로 교체. | **중간.** Minecraft식 블록 파괴와 유사하나 자연스럽지 않음. 미리 정해진 형태만 가능. |
| **CSG (Constructive Solid Geometry)** | 구체/박스 CSG를 지형에 불리언 연산으로 적용. Godot 4에 CSG 노드 내장. | **낮음.** CSG는 에디터 도구이며 런타임 성능이 매우 나쁨. 대량 편집 불가. |
| **"가짜 채굴"** | 채굴 지점에 파티클 이펙트 + 자원 드랍만 제공. 지형은 변하지 않음. | **최저.** Project Nomad의 하드SF 생존 컨셉과 완전히 배치. |
| **제한된 채굴 구역** | 특정 "광맥" 오브젝트만 채굴 가능. 지형 자체는 불변. | **중간.** Subnautica 방식. 구현 간단하지만 Astroneer급 자유도 없음. |

#### 결론

**복셀 없이 Project Nomad 수준의 채굴을 구현하는 것은 사실상 불가능하다.**

Project Nomad의 채굴은 단순히 "자원을 얻는 행위"가 아니라, **"왜소행성의 지하를 탐험하며 광맥을 찾고, 터널을 파서 접근하는"** 전체적인 경험이다. GDD에 명시된 채굴 도구(곡괭이 → 드릴 → 레이저)의 진행은 점진적으로 더 많은 지형을 변형할 수 있게 되는 것을 전제한다.

**만약 채굴 자유도를 포기한다면**, 게임의 정체성이 "하드SF 생존 크래프팅"에서 "SF 건설 시뮬레이션"으로 변질된다.

### 3.2 동굴을 복셀 없이 만들 수 있는가?

#### 가능한 대안들

| 방식 | 설명 | 적합도 |
|------|------|--------|
| **프리팹 동굴 메시** | 동굴 구조를 미리 모델링한 3D 메시로 배치. 하이트맵 아래에 별도 레이어로 존재. | **높음.** 비주얼 품질 우수. 레벨 디자인 가능. 그러나 **절차적 생성 불가**, 모든 동굴을 수동 설계. |
| **Procedural Mesh Generation** | 런타임에 노이즈 기반으로 동굴 메시를 절차적 생성. | **중간.** 기술적으로 가능하나, 사실상 "복셀 없는 마칭 큐브"와 다를 바 없어 복잡도는 동일. |
| **인스턴스 스티칭(Instance Stitching)** | 동굴 세그먼트 프리팹을 절차적으로 연결. | **중간.** 제한된 형태의 절차적 동굴 가능. 반복감이 강할 수 있음. |

#### 결론

**복셀 없이 동굴은 만들 수 있지만, "채굴로 뚫어 들어가는 동굴"은 불가능하다.**

프리팹 동굴은 레벨 디자인된 공간으로만 존재하며, 플레이어가 자유롭게 벽을 파서 새로운 통로를 만드는 것은 복셀 시스템 없이는 구현할 수 없다. Project Nomad에서 동굴은 "발견하는" 것이 아니라 "파 내려가는" 것이므로, 복셀이 필수다.

### 3.3 구형 행성을 하이트맵으로 만들 수 있는가?

#### Cube Sphere 기법

이론적으로 **가능하다.** 정육면체의 6면을 각각 하이트맵으로 구성하고, 정규화(normalize)하여 구형으로 투영하는 방식이다.

```
    ┌───┐
    │ T │       T = Top
┌───┼───┼───┐   F = Front
│ L │ F │ R │   B = Back
└───┼───┼───┘   L = Left
    │ Bo│       R = Right
    └───┘       Bo = Bottom
      │
    ┌───┐
    │ Bk│
    └───┘
```

#### 구현 과제

1. **6면 경계 스티칭.** 면과 면이 만나는 모서리에서 하이트맵 값이 연속적이어야 함. 불연속 시 이음새가 보임.
2. **극점 왜곡.** 큐브의 꼭짓점 부근에서 텍셀(texel) 밀도가 불균일해짐.
3. **LOD 시스템.** 각 면을 쿼드트리로 분할하여 LOD 관리. 기존 Terrain3D가 지원하지 않으므로 직접 구현.
4. **구면 좌표 매핑.** 노이즈 함수, 바이옴 분포 등을 구면 좌표로 변환해야 함.
5. **물리/충돌.** Godot의 기본 물리는 평면 지형을 가정하므로, 구면 충돌 감지를 직접 구현.

#### 결론

**구형 행성 자체는 하이트맵으로 만들 수 있지만, "채굴 가능한 구형 행성"은 불가능하다.**

하이트맵 구형 행성은 "우주에서 행성을 보는" 비주얼과 "지표면 위를 걷는" 경험만 제공한다. 지하 공간, 채굴, 동굴은 하이트맵의 본질적 한계로 불가능하다.

### 3.4 종합: 복셀 포기 시 잃는 것 vs 얻는 것

| 잃는 것 | 얻는 것 |
|---------|---------|
| 자유로운 채굴 (터널, 수직갱) | 개발 단순화 (복셀 시스템 불필요) |
| 절차적 동굴 | 성능 향상 (하이트맵은 훨씬 가벼움) |
| 오버행/아치 등 3D 지형 | 텍스처링 용이 (하이트맵은 표준 UV 매핑) |
| 플레이어 주도 지형 변형 | 에셋 호환성 향상 |
| **게임의 핵심 정체성** | -- |

**최종 판단: 복셀은 포기할 수 없다.** Project Nomad의 핵심 루프(채굴 → 제련 → 제작)에서 채굴이 복셀에 의존하며, "왜소행성의 지하를 탐험한다"는 서사적 경험이 복셀 지형 편집 없이는 성립하지 않는다.

## 4. 최종 권고안

### 4.1 1순위 추천: Godot + VoxelTools 유지 (현재 스택 계속)

#### 근거

| 요소 | 평가 |
|------|------|
| **시간 비용** | 엔진 전환 시 최소 3-6개월 손실. 현재 스택은 이미 학습 완료. |
| **금전 비용** | $0. UE5 전환 시 $349(Voxel Plugin) + 미래 로열티. |
| **기술 적합도** | 구형 행성, 런타임 편집, LOD, Double Precision -- 모든 핵심 요구사항 충족. |
| **리스크** | 800km 스케일 미검증이 최대 리스크이나, 스케일 다운(80km)으로 완화 가능. |
| **기회비용** | 엔진 전환에 쓸 시간으로 **게임 콘텐츠를 만들 수 있다.** |

#### 구체적 행동 계획

1. **2주 프로토타입** (이미 합의된 Phase 1)
   - 400km 반경 행성 생성 + Double Precision 빌드 검증
   - 크레이터 3개 이상 SDF 기반 생성
   - 바이옴 2개(얼음 평원 / 톨린 분지) 구면 좌표 기반 분포
   - 런타임 채굴 테스트 (do_sphere 성능 측정)

2. **프로토타입 성공 시:** 개발 계속. 아트 스타일 정립에 집중.
3. **프로토타입 실패 시 (800km 불가):**
   - **Plan A:** 스케일 다운 80km. 게임플레이 영향 최소화.
   - **Plan B:** 스케일 다운 20km (solar_system_demo 검증 범위). 매스 드라이버 규모 조정.
   - **Plan C (최후 수단):** UE5 + Voxel Plugin 전환.

#### 좌절감 해소를 위한 구체적 조치

현재 느끼는 좌절감의 대부분은 **"VoxelTools의 한계"가 아니라 "올바른 사용법을 모르는 것"**에서 기인할 가능성이 높다:

1. **크레이터:** VoxelGeneratorGraph에서 `SdfSphere(반전) + Noise(가장자리)` 조합. 구면 좌표로 위치 지정.
2. **바이옴 크기:** 바이옴 분포 노이즈의 frequency를 낮추면 큰 바이옴, 높이면 작은 바이옴. `FastNoiseLite`의 `frequency` 파라미터 조절.
3. **동굴:** 3D 노이즈 임계값 방식. `noise_3d(pos) > threshold`인 영역을 공동(cavity)으로 처리.
4. **비주얼:** Godot의 후처리 파이프라인(톤 매핑, 블룸, 볼류메트릭 포그)을 적극 활용. "분위기는 렌더러가 아니라 아트 디렉션이 만든다."

### 4.3 "이것만은 하지 마라" 경고

#### 경고 1: Unity에서 복셀 엔진 자체 개발 금지

Planet Nomads의 Sandy Engine은 **전업 팀이 수년간** 개발한 결과물이다. 솔로 개발자가 이를 재현하려는 시도는 게임 개발이 아니라 **엔진 개발**이 되어버린다. Planet Nomads 자체도 기술 개발에 과도한 시간을 투자하여 결국 콘텐츠 부족으로 개발이 사실상 중단되었다.

#### 경고 2: Rust로 커스텀 복셀 엔진 개발 금지

"더 나은 도구를 직접 만들겠다"는 유혹은 프로그래머의 가장 큰 함정이다. VoxelTools는 7년간 약 5,000 커밋의 성숙한 C++ 모듈이다. 이를 Rust로 재현하는 것은 **최소 1-2년의 전업 엔진 프로그래밍**이며, 그 시간에 게임을 완성할 수 있다.

#### 경고 3: 복셀 포기하고 하이트맵으로 전환 금지

Project Nomad의 핵심 메카닉(채굴, 동굴 탐험, 지형 변형)이 모두 복셀에 의존한다. 하이트맵으로 전환하면 게임의 정체성이 소멸하며, **다른 게임을 만드는 것**과 같다.

#### 경고 4: "비주얼 품질 최우선"이라고 UE5로 뛰지 마라

분위기(atmosphere)는 렌더링 엔진의 성능이 아니라 **아트 디렉션, 조명 설계, 색채 팔레트, 사운드 디자인**의 합산이다. Astroneer는 UE4에서 텍스처 없이도 강렬한 분위기를 만들었고, Limbo/Inside는 Unity에서 흑백 2D로도 걸작을 만들었다. Godot 4 Forward+의 후처리 파이프라인(톤 매핑, 블룸, 볼류메트릭 포그, 커스텀 셰이더)은 **Project Nomad의 "고독한 왜소행성"** 분위기를 만들기에 충분하다.

#### 경고 5: 행성 크기에 집착하지 마라

800km가 반드시 필요한가를 진지하게 질문해야 한다. Astroneer는 수 km 행성으로 500만 장 팔았다. 80km로도 충분히 광활한 느낌을 줄 수 있으며, 플레이어가 실제로 탐험하는 영역은 행성 전체의 극히 일부다. **밀도 높은 작은 세계가 텅 빈 거대한 세계보다 낫다.**
