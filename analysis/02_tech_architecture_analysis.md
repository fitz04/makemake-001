## 1. Godot + Zylann VoxelTools 심층 분석

### 1.1 현재 성숙도 및 안정성

#### 개발 현황 (2026년 3월 기준)

Zylann VoxelTools는 **4,907 커밋**, **10개 릴리스**를 거친 성숙한 C++ 모듈이다. 최신 빌드는 **Godot 4.6 stable + Voxel Tools 1.6** (2026년 2월)으로, Godot 4의 최신 안정 버전과 동기화되어 있다.

| 항목 | 상태 |
|------|------|
| Godot 4 지원 | Godot 4.6 stable 완전 지원 |
| 배포 방식 | Module (권장) / GDExtension (실험적) |
| 주요 언어 | C++ 93.1%, GDShader 2.2% |
| 라이선스 | MIT |
| 유지보수 | 1인 개발자(Marc Gilleron) 중심, 활발한 커뮤니티 |

**GDExtension vs Module 차이점:**
- **Module:** 커스텀 Godot 빌드 필요. 안정적이고 테스트가 충분함. **권장 방식.**
- **GDExtension:** Godot 4.4.1+ 지원. 별도 빌드 불필요하나 테스트가 부족하여 Module에 없는 버그가 존재할 수 있음.

**평가:** 솔로 개발자 1인이 만든 플러그인이라는 점은 리스크 요인이지만, 7년 이상의 개발 역사와 활발한 GitHub 활동, solar_system_demo라는 검증된 레퍼런스가 존재한다. 상용 게임 출시 사례가 제한적이라는 점은 주의가 필요하다.

#### 핵심 기능 목록

- **지형 유형:** VoxelLodTerrain (부드러운 LOD 지형), VoxelTerrain (블록형 Minecraft식)
- **메시 생성:** Transvoxel 알고리즘 (부드러운 등가면), 블록형 메시
- **복셀 채널:** 8비트/16비트 저장
- **LOD:** 청크 기반 Level of Detail, 거리 기반 자동 조절
- **스트리밍:** 무한 지형 생성, 청크 페이징 (로드/언로드)
- **인스턴싱:** 풀, 바위 등 장식물 자동 배치
- **물리:** Godot 물리 통합 + Minecraft식 빠른 충돌 대안
- **에디터:** 런타임 지형 편집 (터널, 오버행, 동굴)

### 1.2 solar_system_demo 실제 기능 범위

Zylann의 solar_system_demo는 Project Nomad의 기술적 가능성을 증명하는 **가장 중요한 레퍼런스**이다.

#### 데모 사양

| 항목 | 사양 |
|------|------|
| 행성 수 | 4개 행성 + 1개 위성 |
| 행성 반경 | 1~2km (표준), 10~20km (x10 모드) |
| 전체 시스템 크기 | ~50km |
| Origin Shifting | 구현됨 (행성 접근 시 자동 트리거) |
| 지형 편집 | 실시간 복셀 파괴/건설 |
| 대기 | 볼류메트릭 구름 포함 |
| 우주선 | 지상~궤도 비행 전환 |
| 캐릭터 | 3인칭 이동, 파기/건설 |
| 성능 기준 | Ryzen 5 2600 + GTX 1060: 60FPS, ~1GB RAM, 5초 시작 |

#### 이 게임에 직접 적용 가능한 기능

기존 문서("대규모 행성을 위한 오브젝트 및 지형 배치 전략")에서 이미 정리한 바와 같이:

1. **전략 1 (하이브리드 Mesh+Voxel):** 건물은 일반 3D 메시, 지반만 복셀로 평탄화. solar_system_demo의 우주선 이착륙 코드가 직접 참조 가능.
2. **전략 2 (생성기 레벨 합성):** VoxelGenerator 내에서 템플릿을 buffer.paste_into()로 합성. 런타임 paste_block()의 20배 물리 메시 비용을 완전 회피.
3. **구면 정렬:** RayCast 기반 표면 법선 계산으로 둥근 행성 표면에 오브젝트 밀착.
4. **행성 중력:** 구면 중력 벡터 계산 로직.

#### 데모의 한계

- **행성 크기:** 최대 20km. Project Nomad의 800km과는 **40배 차이.**
- **물리 불안정:** 대규모 행성 스케일에서 물리 동작이 불안정하다고 명시됨.
- **지형 충돌:** 빌딩 중 자기매장 시 충돌 감지 미작동.
- **게임플레이:** 기술 데모 수준이며 실제 게임 메카닉은 없음.

### 1.3 800km 행성 구현 시 기술적 한계와 해결책

이것이 Project Nomad의 **가장 큰 기술적 도전**이다.

#### 문제 1: 부동소수점 정밀도

32비트 float는 23비트 정밀도를 가진다. 원점에서의 거리별 정밀도 한계:

| 원점 거리 | 연속 부동소수점 간격 | 실용성 |
|-----------|---------------------|--------|
| 1 km | ~0.0001m | 완벽 |
| 10 km | ~0.001m | 양호 |
| 100 km | ~0.01m | 주의 필요 |
| 400 km (800km 행성 반경) | ~0.05m | **시각적 결함 발생** |
| 512 km | ~0.06m | **메시 떨림(jitter) 심각** |

800km 행성의 중심을 원점으로 두면, 표면은 원점에서 ~400km 떨어지게 되어 **약 5cm 단위로 정밀도가 떨어진다.** 캐릭터 이동, 애니메이션, 물리가 심각하게 오작동한다.

#### 해결책: Double Precision 빌드 + Origin Shifting

**Godot 4.0+부터 이중 정밀도(double precision) 빌드가 공식 지원된다.** `precision=double` 플래그로 컴파일하면:

- 오브젝트 위치가 64비트 double로 처리됨
- GPU 전송 시 double을 두 개의 float로 분할하여 정밀도 유지 (Godot의 GPU 이중정밀 에뮬레이션)
- 수십억 유닛 거리에서도 메시 안정성 보장

**Voxel Tools 역시 double 빌드를 지원한다** -- Zylann이 `double` 버전 빌드를 별도로 제공하고 있다.

**그러나 주의점:**
- 공식 Godot 빌드에는 double precision이 포함되지 않음. **커스텀 빌드 필수.**
- `skip_vertex_transform` 모드와 비호환
- 사용자 셰이더 내부의 연산은 여전히 single precision
- 정점(vertex) 수준 정밀도 문제는 별도 해결 필요

**추가 해결책: Origin Shifting (원점 이동)**

solar_system_demo가 이미 구현한 방식:
- 플레이어 위치를 항상 원점 근처로 유지
- 전체 월드를 역방향으로 이동
- 복셀 블록/청크 좌표는 정수(int) 기반이므로 영향 없음

**800km 행성에 대한 권장 전략:**
1. Double precision 빌드 사용
2. Origin Shifting을 플레이어 이동에 연동
3. 행성 반경 단위로 Sector 분할 (예: 64개 섹터)
4. 활성 섹터만 상세 메시 생성, 나머지는 임포스터(impostor) 처리

#### 문제 2: 복셀 데이터 볼륨

800km 행성의 표면적은 약 **2,010,000 km^2**이다. 1m 해상도로 전체를 복셀화하면 메모리가 폭발한다.

**해결책:**
- **절차적 생성 전용:** 복셀 데이터를 저장하지 않고, VoxelGenerator에서 노이즈 기반으로 실시간 생성
- **변경분만 저장:** 플레이어가 수정한 영역만 VoxelStream으로 디스크에 기록
- **LOD 활용:** 원거리 청크는 낮은 해상도로 생성 (VoxelLodTerrain의 기본 기능)
- **활성 영역 제한:** 플레이어 반경 수 km만 상세 복셀 유지

이 방식은 solar_system_demo에서 이미 검증되었으며, 800km으로 확장하더라도 **로드된 청크 수는 동일하게 유지**된다 (플레이어 시야 범위 기반).

#### 문제 3: LOD 전환 품질

800km 행성에서는 LOD 레벨이 매우 많아야 한다 (표면 1m ~ 궤도에서 수 km 단위까지).

**VoxelLodTerrain의 LOD 지원:**
- 자동 LOD 레벨 관리
- Transvoxel 알고리즘으로 LOD 경계면 매끈한 전환
- 그러나 **매우 높은 LOD 레벨(10+)에서의 안정성은 미검증**

### 1.4 LOD, 물리, Origin Shifting 지원 현황 요약

| 기능 | 지원 상태 | Project Nomad 적합도 | 비고 |
|------|-----------|---------------------|------|
| LOD (VoxelLodTerrain) | 완전 지원 | 높음 | Transvoxel 기반 부드러운 전환 |
| Origin Shifting | 구현 (solar_system_demo) | 높음 | 커스텀 구현 필요 |
| Double Precision | 지원 (커스텀 빌드) | 필수 | 800km에는 반드시 필요 |
| Godot 물리 통합 | 지원 | 중간 | 대규모에서 불안정 보고 |
| 런타임 편집 | 지원 | 높음 | 물리 메시 재생성 비용 주의 |
| 지형 저장/로드 | VoxelStream | 높음 | 변경분만 저장하는 전략 가능 |
| 구면 지형 | 지원 | 높음 | 구면 노이즈 기반 생성 |

### 1.5 후처리(Post-processing) 파이프라인 능력

Godot 4는 Forward+ 렌더러에서 상당히 풍부한 후처리 효과를 제공한다.

#### 내장 후처리 효과 목록

| 효과 | 지원 여부 | 렌더러 제한 |
|------|-----------|-------------|
| **Tone Mapping** (Linear, Reinhard, Filmic, ACES) | 완전 지원 | 모든 렌더러 |
| **Glow/Bloom** | 완전 지원 | 모든 렌더러 |
| **Color Correction** (밝기, 대비, 채도) | 완전 지원 | 모든 렌더러 |
| **SSAO** (Screen-Space Ambient Occlusion) | 완전 지원 | Forward+ |
| **SSIL** (Screen-Space Indirect Lighting) | 완전 지원 | Forward+ |
| **SSR** (Screen-Space Reflections) | 완전 지원 | Forward+ |
| **SDFGI** (Signed Distance Field GI) | 완전 지원 | Forward+ |
| **Volumetric Fog** | 완전 지원 | Forward+ |
| **Depth of Field** | 완전 지원 | Forward+ |
| **비체적 안개** (Standard Fog) | 완전 지원 | 모든 렌더러 |
| **커스텀 후처리 셰이더** | 완전 지원 | 모든 렌더러 |

#### 대기 산란 (Atmospheric Scattering)

내장 기능은 아니지만, **Zylann이 별도로 제작한 godot_atmosphere_shader 플러그인**이 존재:

- **Godot 4.3+ 호환**
- **광산란(Light Scattering) 기반** 물리적 대기 시뮬레이션
- **볼류메트릭 구름** 지원 (표준/고품질/레이마칭 조명 등 7개 셰이더 변형)
- **행성 내부에서 안개처럼 보이도록** 렌더링 가능
- **적응형 LOD:** 원거리에서 큐브 메시로 전환하여 다중 행성 대기 저비용 렌더링
- **제한사항:** Compatibility 렌더러 미지원, 에디터 프리뷰 행성 근접 시 오류, 볼류메트릭 구름은 "아직 불완전"

**평가:** 카이퍼벨트 왜소행성은 대기가 없으므로 대기 산란은 불필요하지만, **우주 공간에서 행성 실루엣/림 라이팅**, **분출구 가스 효과**, **거주구 내부 안개** 등에 볼류메트릭 포그와 커스텀 셰이더를 활용할 수 있다.

#### 커스텀 후처리

Godot 4는 `CompositorEffect`와 셰이더 기반 커스텀 후처리를 완전 지원한다. 화면 전체에 걸리는 색보정, 왜곡, 스캔라인, 노이즈 등 원하는 모든 효과를 구현할 수 있다.

## 2. Unity 대안 분석

### 2.1 Unity에서 동일 게임 구현 시 장단점

#### 장점

| 항목 | 설명 |
|------|------|
| **3D 렌더링 성숙도** | Godot 대비 3D 렌더링에서 여전히 우위. 특히 HDRP의 시각적 품질. |
| **에셋 스토어** | 에셋구매계획 문서에서 이미 확인한 바와 같이 산업/모듈형/하드SF 에셋이 풍부. |
| **문서/튜토리얼** | 방대한 학습 자료. 복셀 행성 구현에 대한 GDC 발표, 기술 블로그 다수. |
| **멀티스레딩** | Jobs/Burst 시스템으로 복셀 메시 생성 최적화 가능. |
| **콘솔 배포** | PS5, Xbox, Switch 직접 빌드 지원. |
| **Planet Nomads 선례** | Unity에서 120km 직경 구형 복셀 행성을 구현한 **실제 상용 게임 사례**가 존재. |

#### 단점

| 항목 | 설명 |
|------|------|
| **라이선스 비용** | 개인용 무료(연매출 $200K 미만). Pro는 연 $2,200/석. 성공 시 비용 발생. |
| **에셋 변환** | 에셋구매계획 문서에 명시된 대로, Unity 에셋을 Godot으로 가져오려면 FBX Export 과정 필요. 반대로 Unity를 쓰면 이 문제가 사라짐. |
| **에디터 속도** | 에셋 리임포트에 30초 이상. Godot의 120MB 즉시 실행 대비 무거움. |
| **복셀 엔진 자체 개발** | Zylann VoxelTools처럼 통합된 복셀 솔루션이 없음. 커스텀 개발 또는 서드파티 플러그인 필요. |
| **런타임 변경** | Unity의 Terrain 시스템은 런타임 편집에 적합하지 않음. 복셀 시스템 자체 구현 필수. |

### 2.2 Voxel 플러그인 생태계

#### Voxeland

- **가격:** Unity Asset Store 유료
- **방식:** 세분화된 큐브형 복셀을 평활화
- **특징:** MapMagic과 연동 가능, 무한 지형 절차적 생성 지원
- **한계:** 구형 행성 지원이 기본 내장되지 않음. 평면 지형에 최적화. 최근 업데이트가 2024년으로 활발하지 않음.

#### uTerrains (Ultimate Terrains)

- **방식:** Adaptive Dual Contouring
- **특징:** 부드러운 지형, LOD 지원
- **한계:** 구형 행성 용도로 설계되지 않음. 커스텀 수정 필요.

#### Voxelica

- **Unity Asset Store 최신 복셀 엔진**
- 정보가 제한적이나, Marching Cubes 기반으로 보임.

#### 커스텀 솔루션 (Planet Nomads 방식)

Planet Nomads 팀이 증명한 접근법:
- **C++ 플러그인(Sandy Engine)** 으로 순수 Unity 대비 50% 성능 향상
- **Modified Marching Cubes** + 옥트리 청크 관리
- 청크 크기 16m~128km, 최소 복셀 해상도 1m
- **R-Tree + SQLite** 로 수정 이력 지리적 인덱싱
- 가시 거리 2km, 최대 속도 120km/h 유지 가능

**평가:** Unity에서 800km 행성 복셀 시스템을 구현하려면 **사실상 자체 엔진을 개발해야 한다.** Planet Nomads 팀은 전업 팀이었으며, 솔로 개발자에게는 매우 높은 진입 장벽이다.

### 2.3 에셋 스토어 접근성 (에셋구매계획 문서 참조)

에셋구매계획 문서에서 확인된 핵심 사항:

1. **Unity Asset Store가 메인 에셋 소스:** 인더스트리얼/모듈형/하드SF 에셋이 가장 풍부
2. **Godot 호환 문제:** Unity 에셋을 Godot으로 가져오려면:
   - Unity 설치 -> 에셋 Import -> FBX Exporter로 내보내기 -> Godot 프로젝트에 투입
   - 텍스처 연결 끊어짐 수동 복구 필요
3. **Unity를 선택하면:** 이 변환 과정이 완전히 사라짐. 에셋 스토어에서 바로 사용.
4. **Godot를 선택하면:** Sketchfab(.gltf/.glb 직접 다운로드)과 AmbientCG(PBR 텍스처)가 변환 없이 사용 가능한 대안.

### 2.4 HDRP vs URP 선택

Project Nomad가 Unity를 선택할 경우의 렌더 파이프라인 분석:

| 항목 | URP | HDRP |
|------|-----|------|
| **시각적 품질** | 양호 (인디 게임 수준) | 우수 (시네마틱급) |
| **볼류메트릭 안개** | 미지원 | **완전 지원** |
| **볼류메트릭 구름** | 미지원 | **완전 지원** |
| **레이 트레이싱** | 미지원 | 지원 |
| **SSR/SSAO** | 기본 지원 | 고급 지원 |
| **성능** | 높음 (모바일 포함) | 낮음 (고사양 PC 필요) |
| **하드웨어 요구** | 낮음 | **높음** |
| **셰이더 커스텀** | Shader Graph | Shader Graph + HLSL |
| **커뮤니티 자료** | 풍부 | 상대적으로 적음 |

**권장:** HDRP. Project Nomad는 PC 전용이며, 비주얼 분위기가 최우선이다. 볼류메트릭 효과(분출구 가스, 거주구 내부 안개)와 고급 조명이 핵심 경험이므로 HDRP가 적합하다. 단, HDRP의 복잡성은 솔로 개발자에게 부담이 될 수 있다.

### 2.5 후처리 스택 비교

| 효과 | Godot 4 Forward+ | Unity URP | Unity HDRP |
|------|-------------------|-----------|------------|
| Bloom/Glow | O | O | O |
| Color Grading | O | O | O (LUT 포함) |
| Tone Mapping | O (4종) | O | O (다양) |
| SSAO | O | O | O (고급) |
| SSR | O | O (기본) | O (고급) |
| Volumetric Fog | O | X | **O** |
| Volumetric Clouds | X (커스텀 셰이더) | X | **O** |
| Depth of Field | O | O | O |
| Motion Blur | O | O | O |
| SDFGI | O | X | X (다른 GI 방식) |
| Film Grain | O | O | O |
| Chromatic Aberration | O | O | O |
| 커스텀 후처리 | O (셰이더) | O (Render Feature) | O (Custom Pass) |

**결론:** 내장 볼류메트릭 효과에서 HDRP가 압도적이나, Godot 4도 커스텀 셰이더로 대부분 구현 가능하다. Project Nomad의 진공 환경에서는 볼류메트릭 대기 효과보다 **포인트 라이트 기반 국소 효과**가 더 중요하므로, 엔진 간 격차가 줄어든다.

## 3. 복셀 엔진 vs 전통적 맵 에디터

### 3.1 복셀 방식의 장점

| 장점 | Project Nomad 관련성 |
|------|---------------------|
| **절차적 지형 생성** | 800km 행성을 수동으로 만들 수 없음. **필수.** |
| **지형 변형/채굴** | 드릴+폭파 채굴(Act 3), Living Lode 동굴 탐사. **핵심 메카닉.** |
| **구면 지형** | 행성은 둥글다. 하이트맵은 구면에 부적합. **필수.** |
| **동굴/오버행** | 지하 대수층, Living Lode 서식 동굴. **핵심 컨텐츠.** |
| **런타임 편집** | 기초 공사(지형 평탄화), 건물 배치. **게임플레이 필수.** |
| **무한 지형** | 800km 행성 전체를 한 번에 로드할 수 없음. 스트리밍 필수. |

### 3.2 전통적 방식(Heightmap/메시 배치)의 장점

| 장점 | 설명 |
|------|------|
| **성능** | 하이트맵은 GPU에서 극도로 효율적. LOD 전환도 단순. |
| **아트 컨트롤** | 모든 지형 디테일을 아티스트가 수동 조절 가능. |
| **개발 속도** | 에디터에서 즉시 결과 확인. 복셀 디버깅보다 직관적. |
| **도구 성숙도** | Unity Terrain, Godot Terrain3D 등 검증된 도구. |
| **텍스처링** | 하이트맵 기반 스플래팅이 복셀 텍스처링보다 훨씬 성숙함. |

### 3.3 이 게임의 핵심 메카닉에 최적인 방식

Project Nomad의 핵심 메카닉을 기준으로 평가하면:

| 핵심 메카닉 | 복셀 | 전통적 | 판정 |
|------------|------|--------|------|
| 800km 구면 행성 | **적합** (구면 노이즈) | 부적합 (평면 기반) | **복셀** |
| 드릴+폭파 채굴 | **적합** (런타임 편집) | 불가능 | **복셀** |
| 지하 동굴 탐사 | **적합** (자연스러운 3D 공동) | 어려움 | **복셀** |
| 기지 건설 | 하이브리드 가능 | **적합** | 무승부 |
| 시각적 품질 | 텍스처링 어려움 | **적합** | 전통적 |
| 성능 | 높은 CPU 부하 | **적합** | 전통적 |
| 솔로 개발 효율 | 절차적 생성으로 컨텐츠 자동화 | 수동 제작 필요 | **복셀** |

**결론: 복셀이 필수적이다.**

채굴, 동굴 탐사, 구면 행성이라는 3대 핵심 메카닉이 모두 복셀을 요구한다. 전통적 방식으로는 이 게임의 핵심 경험을 구현할 수 없다.

다만 **하이브리드 접근**(기존 문서의 전략 1)이 최적이다:
- **지형:** 복셀 (VoxelLodTerrain)
- **건물/기계:** 일반 3D 메시 (MeshInstance3D + StaticBody3D)
- **장식물:** 인스턴싱 시스템 (VoxelInstancer)

## 4. 최종 권고안

### 4.1 1순위 권장: Godot 4.6 + Zylann VoxelTools (Double Precision 빌드)

**근거:**

1. **복셀 시스템 통합 완성도:** VoxelLodTerrain은 구면 행성, LOD, 스트리밍, 런타임 편집을 **하나의 통합 솔루션**으로 제공. Unity에서는 이 모든 것을 자체 구현해야 함.

2. **solar_system_demo 레퍼런스:** 코드 수준에서 참조 가능한 구체적인 구현 예시가 존재. Origin Shifting, 구면 중력, 우주선 전환 등 Project Nomad에 필요한 핵심 기술이 이미 시연됨.

3. **기존 연구와의 일치:** 개발자가 이미 "대규모 행성을 위한 오브젝트 및 지형 배치 전략" 문서를 작성하며 VoxelTools의 아키텍처를 깊이 이해하고 있음. 이 학습 투자를 활용해야 함.

4. **비용:** 완전 무료(MIT). 성공 시에도 라이선스 비용 없음.

5. **개발 속도:** 에디터 120MB, 즉시 시작, 빠른 이터레이션. 18개월 개발 주기에서 누적 시간 절약이 큼.

6. **후처리:** Forward+ 렌더러의 내장 효과 + Zylann 대기 셰이더 + 커스텀 후처리로 카이퍼벨트 분위기 구현에 충분.

**리스크:**

| 리스크 | 심각도 | 완화 방안 |
|--------|--------|-----------|
| 800km 스케일 미검증 | **높음** | 초기 프로토타입에서 400km 반경 테스트 수행. 실패 시 스케일 축소 (80km) 검토. |
| 1인 유지보수자 의존 | 중간 | MIT 라이선스이므로 포크 가능. C++ 코드 직접 수정 가능성 확보. |
| GDExtension 불안정 | 낮음 | Module 빌드 사용으로 회피. |
| Double Precision 빌드 | 중간 | Zylann이 double 빌드를 공식 제공. 빌드 파이프라인 초기 구축 필요. |
| 복셀 텍스처링 품질 | 중간 | Triplanar mapping + 커스텀 셰이더. 완벽하지는 않지만 왜소행성의 단조로운 표면에는 충분. |

## 5. 비주얼 분위기 구현 전략

### 5.1 카이퍼벨트 왜소행성의 비주얼 아이덴티티

GDD에서 정의된 환경 조건을 시각적으로 번역하면:

#### 5.1.1 -230도C, 진공, 얼음

**시각적 표현:**
- **극저온 색감:** 전체적으로 차갑고 채도가 낮은 팔레트. 파란-보라 언더톤.
- **얼음 표면:** 질소 얼음(우윳빛/창백한 푸른색), 메탄 얼음(호박색/오렌지색), 물 얼음(투명~백색). 각각 다른 PBR 소재로 구분.
- **열 대비:** 기지 내부의 따뜻한 조명(주황/노랑)과 외부의 차가운 색감 극대화. 발전기 화덕의 붉은 빛이 틈새로 새어나오는 연출.
- **진공의 날카로움:** 대기 산란이 없으므로 그림자가 칼날처럼 날카로움. 그림자 softness를 0에 가깝게 설정. 태양빛이 닿는 면과 그림자 면의 명암비 극대화.

**기술 구현:**
```
Godot: DirectionalLight3D.shadow_blur = 0.0
       WorldEnvironment.ambient_light_color = Color(0.02, 0.02, 0.05)
       WorldEnvironment.ambient_light_energy = 0.05 (매우 낮음)
```

#### 5.1.2 붉은 톨린 먼지

**시각적 표현:**
- GDD(추가설정노트)에서 정의: "검붉은색 코코아 가루 질감. 정전기로 뭉쳐 있음."
- 지형의 기본 색상을 붉은-갈색 톨린으로 설정. AmbientCG의 Ground037 (갈라진 땅) 텍스처 활용.
- 정전기 먼지가 장비에 쌓이는 시각 효과 (파티클 시스템).

**기술 구현:**
- **Triplanar Mapping** 셰이더로 복셀 지형에 톨린 텍스처 적용
- 높이/경사도 기반 텍스처 블렌딩 (톨린 먼지 vs 얼음 노출 암반)
- 발밑 먼지 파티클 (저중력으로 느리게 퍼짐, 대류 없으므로 직선 궤적)

#### 5.1.3 우주 배경 (은하수, 태양의 먼 빛)

**시각적 표현:**
- **태양:** 45.8 AU 거리에서 태양은 밝은 점. 지구에서의 약 **1/2100** 밝기. 보름달보다 약간 밝은 수준.
- **은하수:** 대기가 없으므로 은하수가 극도로 선명. 스카이박스의 핵심.
- **별:** 깜빡이지 않음 (대기 없음). 정적인 점으로 렌더링.
- **다른 카이퍼벨트 천체:** 마케마케 등이 밤하늘에 보일 수 있음.

**기술 구현:**
- **HDR 스카이박스:** 실제 은하수 HDR 이미지 기반 PanoramaSky
- **태양 DirectionalLight3D:** 매우 낮은 energy (0.3~0.5), 약간 따뜻한 색온도
- **별 파노라마:** 고해상도 8K+ 별 필드 텍스처
- **렌즈 플레어:** solar_system_demo에서 이미 구현한 SIsilicon 포트 렌즈 플레어 활용

#### 5.1.4 정전기 폭풍 (Terminator Event)

GDD(Act1 개발 노트)에서 정의:
- 실제 시간 1시간 주기(일출/일몰), 5분간 지속
- 터미네이터 라인의 정전기를 우주선 선체로 수집

**시각적 표현:**
- 지표면에서 정전기 방전 아크가 튀는 효과 (파티클 + 라이트닝 셰이더)
- 화면 전체에 미세한 노이즈/글리치 효과 (커스텀 후처리)
- 정전기로 먼지가 일어서는 효과 (GPU 파티클)
- 하늘에 오로라 같은 전리층 발광 (커스텀 셰이더)
- 화면 가장자리 크로매틱 어베레이션 증가

**기술 구현:**
- GPU 파티클로 먼지/방전 효과
- 커스텀 후처리 셰이더: 화면 글리치, 스캔라인, RGB 분리
- OmniLight3D 배열로 번개 효과
- AnimationPlayer로 시간 기반 이벤트 제어

#### 5.1.5 분출구 효과

GDD에서: "늙고 병든 균열(Fissure). 출력 미약."

**시각적 표현:**
- 균열에서 올라오는 가스 제트 (진공에서는 급격히 팽창하는 원뿔형)
- 가스가 즉시 승화/결정화되면서 반짝이는 얼음 입자로 변환
- 균열 주변 따뜻한 색감 (지열에 의한 약간의 적외선 느낌)
- 주기적 분출 (간헐천 패턴)

**기술 구현:**
- GPUParticles3D: 원뿔형 분출 + 결정화 파티클 전환
- Volumetric Fog (FogVolume): 분출구 주변 국소 안개
- 점광원(OmniLight3D): 분출 시 순간적 조명
- 셰이더: 지표면 균열 이미시브(emissive) 텍스처

### 5.2 후처리 파이프라인 제안

Project Nomad의 비주얼 목표에 맞춘 Godot 4 후처리 파이프라인:

```
[렌더링 파이프라인]

1. 기본 렌더링 (Forward+)
   ├── 복셀 지형 (Triplanar PBR)
   ├── 메시 오브젝트 (Standard PBR)
   ├── GPU 파티클 (먼지, 가스, 방전)
   └── 스카이박스 (HDR Panorama)

2. 조명 패스
   ├── DirectionalLight (태양: 매우 약함)
   ├── OmniLight 배열 (기지 조명, 발전기 불빛)
   ├── SpotLight (헬멧 랜턴, 로버 헤드라이트)
   └── SDFGI (기지 내부 GI) 또는 LightmapGI

3. 후처리 스택 (순서)
   ├── SSAO (강도: 높음 - 동굴/기지 내부 깊이감)
   ├── SSIL (중간 - 간접광 보완)
   ├── SSR (낮음 - 얼음 표면 반사)
   ├── Volumetric Fog (국소 - 분출구, 거주구 내부만)
   ├── Glow/Bloom (임계치 높음 - 밝은 광원만 블룸)
   ├── Tone Mapping (ACES Filmic)
   ├── Color Correction
   │   ├── 외부: 차가운 색온도, 낮은 채도
   │   ├── 내부: 따뜻한 색온도, 높은 채도
   │   └── 전환: 에어락 통과 시 점진적 전환
   ├── Film Grain (약간 - 우주의 고에너지 입자 느낌)
   └── Vignette (약간 - 헬멧 시야 제한 암시)

4. 특수 상황 후처리
   ├── 정전기 폭풍: 글리치 + 크로매틱 어베레이션 + 스캔라인
   ├── 사기(Morale) 저하: 채도 감소 + 비네트 강화
   ├── 사기 향상: 채도 증가 + 빛나는 테두리
   └── 허기: 화면 흔들림 + 블러
```

## 6. 토론 포인트

### 6.1 게임 디자이너와 논의해야 할 기술적 제약/기회

#### 행성 스케일 vs 플레이 가능 영역

**제약:** 800km 직경 행성의 표면적은 ~2,010,000 km^2이다. 이 중 플레이어가 실제로 방문하는 영역은 극히 일부이다.

**논의 사항:**
- **스케일 축소 가능성:** 행성 직경을 80~100km로 줄이면 기술적 리스크가 대폭 감소하면서도 "거대 행성" 느낌은 유지됨. 도보 탐사 반경 5km, 로버 탐사 반경 50km이면 80km 행성으로도 충분한 탐사 공간.
- **매스 드라이버 엔딩:** 2,500km 둘레 레일 건설은 800km 행성에서만 가능. 스케일 축소 시 레일 길이도 조정 필요.
- **뮤온 촉매 엔딩:** 10km 둘레 가속기는 어떤 스케일에서도 가능.
- **권장:** 프로토타입에서 80km과 800km 모두 테스트 후, 기술적 안정성과 게임플레이 임팩트를 비교하여 결정.

#### 채굴 깊이 제한

**제약:** 복셀 해상도와 LOD 시스템에 따라 플레이어가 파고 들어갈 수 있는 깊이에 제한이 있다. 무한정 파기를 허용하면 메모리/성능 문제 발생.

**논의 사항:**
- 최대 채굴 깊이를 게임플레이적으로 정의 (예: 지표면에서 200m)
- 깊이 제한의 내러티브 정당화 (예: 암반 경도 급증, 방사선 위험 구역)
- Living Lode 동굴은 미리 생성된 템플릿(전략 2)으로 배치하여 깊은 지하 구현

#### 건물 영구성 vs 지형 파괴

**제약:** 하이브리드 시스템에서 건물(메시)은 파괴 불가능하고, 지형(복셀)은 파괴 가능하다. 건물 아래 지형을 파면 건물이 공중에 뜰 수 있다.

**논의 사항:**
- 건물 기초 영역을 "보호 구역"으로 설정 (기존 문서의 전략 1에 이미 포함)
- 건물 해체 메카닉 도입 여부
- 적대 세력 부재이므로 건물 파괴 시나리오가 게임플레이에 미포함?

#### 로딩 시간과 청크 생성

**제약:** 800km 행성에서 120km/h 로버로 이동하면, 청크 생성이 이동 속도를 따라잡아야 한다. Planet Nomads에서도 이것이 핵심 과제였다 (가시거리 2km, 120km/h 지원).

**논의 사항:**
- 로버 최대 속도를 제한할지 (예: 60km/h)
- 스팀 드론(D-1)의 50km 비행은 지형 스트리밍에 더 큰 부담 -- 고도에서 LOD로 해결 가능?
- 매스 드라이버 레일 위를 달리는 시퀀스의 성능 계획

### 6.2 내러티브 디자이너와 논의해야 할 기술적 제약/기회

#### AI '케이'의 시각 획득과 렌더링

**기회:** Act 2에서 AI '케이'가 광센서로 시각을 획득하는 순간은 게임의 핵심 감동 포인트이다.

**기술적 구현 기회:**
- 광센서 획득 전: AI의 "시점"을 표현하는 UI가 텍스트 기반 (음성 + 자막)
- 광센서 획득 후: AI가 "본" 것을 HUD에 표시 (위험 감지, 자원 하이라이트, 누출 탐지)
- **포스트 프로세싱 전환:** AI 시각 획득 순간 화면 전체에 짧은 "디지털 부팅" 효과
- AI가 처음 보는 것들에 대해 반응하는 시스템 (새로운 자원 발견 시 "이건 처음 봐요!")

#### 사기(Morale) 시스템의 시각적 표현

GDD에서 정의:
- 사기 저하 시: 화면 채도 감소
- [만성적 혐오] 디버프: 영구적 작업 효율 -15%
- [기름에 튀긴 칩]으로 치료 시: 채도 증가

**기술적 구현:**
- WorldEnvironment의 색보정 파라미터를 사기 값에 연동
- 사기 0%: 거의 흑백 + 비네트 극대화 + 필름 그레인 증가 -> 시각적 "절망"
- 사기 100%: 채도 약간 증가 + 미세한 블룸 -> "희망"
- **내러티브 기회:** 치즈 첫 완성 시 후처리가 극적으로 밝아지는 연출

#### 엔딩 거대 구조물의 시각적 임팩트

**매스 드라이버 (2,500km 레일):**
- 행성 전체를 감싸는 레일을 어떻게 시각적으로 표현할 것인가?
- 궤도에서 바라볼 때 행성 표면의 빛나는 선으로 보이는 연출
- 건설 진행도에 따라 밤에 레일의 불빛이 수평선까지 이어지는 장면
- **기술:** 레일은 복셀이 아닌 메시 인스턴싱으로 구현. LOD 극한 최적화 필요.

**뮤온 촉매 궤도 가속기 (10km, 자기부양):**
- "하늘의 빛나는 고리" -- 행성 하늘에 떠 있는 거대한 링
- 야간에 발광하는 초전도 코일의 푸른 빛
- 뮤온 빔이 지하로 향하는 시각적 표현
- **기술:** 메시 인스턴싱 + Emissive 소재 + Glow/Bloom

#### Living Lode 생명체의 시각적 표현

GDD 백과사전 분류:
- A종(1-5cm): 빠른 대사, **밝은 빛**
- B종(10-50cm): 느린 대사, **희미한 빛**
- C종(5-15m): 극저 대사, **거의 정지**

**기술적 기회:**
- 동굴 내부에서 Living Lode의 자체 발광이 유일한 광원 (조명 없이 탐사하는 경험)
- A종: 파티클 시스템 + 포인트 라이트로 반딧불 같은 효과
- B종: Emissive 텍스처 + 느린 맥동(pulsing) 애니메이션
- C종: 거대한 결정 구조물. 매우 느린 호흡 같은 발광 주기.
- **내러티브 임팩트:** "살아있는 것 같아요" 라는 AI 대사와 함께, 처음 결정이 미세하게 빛나는 순간

### 6.3 기술/기획 공통 논의 사항

#### 저중력(0.06g) 물리의 게임플레이 영향

**기술적 구현:**
- Godot 물리 엔진의 중력 벡터를 구면 중심 방향으로 설정
- 중력 가속도를 지구의 6%로 설정 (0.588 m/s^2)
- 모든 물리 오브젝트에 적용

**게임 디자인 영향:**
- 점프 높이가 ~17배. 10m 점프 가능 -> 낙하 데미지 계산 재설계 필요?
- 투사체(쇳물 튐) 궤적이 거의 직선 -> GDD에서 이미 반영 ("총알처럼 직진")
- 파티클(먼지, 가스)이 매우 느리게 낙하 -> 시각적으로 아름답지만 파티클 수명 연장 필요
- 로버 바퀴 접지력 약화 -> GDD에서 이미 반영 ("접지력(Traction)이 매우 약함")

#### 시간 체계와 라이팅 사이클

**논의 필요:**
- 800km 왜소행성의 자전 주기는? (마케마케 실제: ~22.5시간)
- 게임 내 시간 가속 비율은?
- 일출/일몰의 시각적 표현: 대기가 없으므로 지구와 완전히 다름
  - 일출: 태양이 수평선 위로 올라오면 즉시 밝아짐 (점진적 여명 없음)
  - 석양 색 없음 (산란 없음)
  - 터미네이터 라인이 매우 날카로움
- 정전기 폭풍의 시각적/게임플레이적 연출 타이밍

#### 성능 예산 배분

**솔로 개발자를 위한 현실적 성능 목표:**

| 상황 | 목표 FPS | 주요 부하 |
|------|----------|-----------|
| 기지 내부 | 60+ | 포인트 라이트 다수, SSAO, SSR |
| 지표면 탐사 | 60+ | 복셀 지형 LOD, 파티클 |
| 로버 고속 주행 | 45+ | 청크 스트리밍, LOD 전환 |
| 정전기 폭풍 | 30+ | 파티클 대량, 후처리 |
| 분출구 근접 | 45+ | 볼류메트릭 포그, 파티클 |
| 궤도 -> 착륙 전환 | 30+ | LOD 극한 전환 |

**최소 사양 제안:** GTX 1060 / Ryzen 5 2600 (solar_system_demo 기준 벤치마크)
